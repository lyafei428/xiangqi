# 架构设计

## 1. 三条线，一套底座

```text
                  ┌── 对弈：本地双人 / 联机 / 人机
规则引擎（唯一真相）├── 教学：讲解 + 逐步演示
                  └── 练习：规则判定 + 目标达成
```

规则引擎是纯函数、零依赖的 TypeScript 模块，被前端与后端同时引用。教学不能另做一套"看起来像棋盘"的静态图，练习不能自己写一套走法判断——否则学生学到的走法在真实对局里不成立，这类错误最难被发现。

## 2. 分层

| 层 | 职责 | 约束 |
|---|---|---|
| `src/shared/` | 规则引擎、记谱、局面序列化 | 纯函数，零依赖，不碰 DOM、不碰 Node API |
| `src/client/` | 界面、交互、本地进度 | 只通过引擎算着法，不自己判规则 |
| `src/server/` | 房间、对局状态机、计时、权威判定 | 信任引擎，不信任客户端 |
| `content/` | 课程与练习数据 | 纯 JSON，可独立校对，改文案不动代码 |

## 3. 技术栈

| 选择 | 理由 | 不选什么 |
|---|---|---|
| TypeScript | 前后端共用引擎需要类型一致 | 纯 JS 在规则引擎这种强约束领域会漏 case |
| React + Vite | 组件复用、构建快、生态稳 | Next.js：本项目无 SSR 需求，多一层成本 |
| SVG 渲染棋盘 | 32 个节点，DOM 性能够；命中判定、动画、无障碍都不必自造 | Canvas：要自己实现命中、无障碍、重绘管理 |
| Node 内置 http + `ws` | 房间服务只需 WebSocket | 完整后端框架：v1 路由不超过十个 |
| SQLite（后续批次） | 棋谱与战绩，单文件无运维 | 云数据库：v1 无账号体系 |

前端不使用 UI 组件库、CSS-in-JS 运行时、状态管理框架。对局状态是单一对象，`useReducer` + context 足够；引入这些库的收益抵不上体积和样式对抗成本。

## 5. 数据流

```text
用户点棋盘
  → 客户端把像素坐标换算成棋盘坐标（除以当前 SVG 缩放比）
  → 询问引擎：这枚棋子能走到哪（用于高亮）
  → 用户点落点
  → 本地对局：引擎校验后直接落子
  → 联机对局：只发 {from, to}，服务端校验后广播权威结果
  → 引擎重算新局面、将军状态、终局判定
```

联机对局中客户端永远不自己决定结果。客户端改代码也改不出一步不合法的棋——服务端用同一份引擎重新校验。

## 6. 响应式策略

一套 DOM，CSS 重排，React 状态不动。

| 视口 | 布局 | 面板 |
|---|---|---|
| ≥1024px | 左棋盘 + 右固定侧栏 | 侧栏常驻 |
| 768–1023px | 上棋盘 + 下抽屉 | 抽屉占 40% 高，可收 |
| <768px | 棋盘占满宽 + 底部抽屉 | 抽屉 ≤50% 高，用 `dvh` |

- 棋盘 SVG `viewBox` 固定，容器定尺寸，棋子按比例缩放，永不写死像素。
- 格宽下限 40 CSS px：手机按此定棋盘尺寸，多余空间留白，不继续压小。
- `@container` 容器查询而非只用视口断点：面板变宽变窄时自身重排。
- 手机横屏（`orientation: landscape and max-height: 500px`）：棋盘左、面板右。
- 用 `dvh` 不用 `vh`：手机地址栏收展会让 `vh` 跳变。
- 用 `ResizeObserver` 而非 `resize` 事件重算命中区，旋转屏幕不重挂载组件。

## 7. 性能预算

| 指标 | 目标 | 手段 |
|---|---|---|
| JS 主包 | < 150KB gzip | 规则引擎独立 chunk |
| 首屏 | 手机 4G 快档 < 2s | 首屏只加载棋盘壳 + 当前课 |
| 走子更新 | < 16ms | 棋子节点不重建，只改 transform |
| 单次着法生成 | < 5ms | 超时挪进 Web Worker |
| CLS | < 0.05 | 棋盘占位先定宽高比 |

- 动画只碰 `transform` 与 `opacity`，不碰宽高、不在动画里读布局。
- 课程 JSON 按课拆包，一次请求一课，不进主包。
- 不做提前虚拟化、不做 memo 风暴：90 个交叉点远不到那个量级。

## 8. 里程碑

| 批次 | 内容 | 验收 |
|---|---|---|
| M0 | 规则引擎 + 测试 | 全部走法用例通过；perft 1–4 与公开值逐位一致 |
| M1 | 棋盘组件 + 本地双人 | 浏览器里能下完一局；三档视口切换局面不丢 |
| M2 | 教学框架 + 练习生成器 + 第一二章 | 走法课可演示可练；判定题引擎自证 |
| M3 | 第三至五章内容 | 22 课全部可跑，内容自证测试全绿 |
| M4 | 联机对战 | 两浏览器同房同步；非法着法被拒；断线重连恢复 |
| M5 | 计时、认输求和、棋谱回放、观战 | 关页重开能接着下；棋谱能存能放 |
| M6 | AI 对战 | Web Worker alpha-beta，单步 ≤ 2 秒 |

M0 必须先做且单独验收：引擎错了，教学、练习、联机都在测一个错的东西。

## 9. 内容生产纪律

1. 每个局面必须经引擎验证，不验证的局面不许进 `content/`。
2. 不接 AI 自动生成讲解。术语和杀法定义需要准确，说反了的讲解比没有讲解更坏。
3. 每课标注来源：取自公认教材的写清出处，自编的写明自编。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 长将长捉判罚版本差异 | v1 简化判罚，规则页明示版本 |
| 断线导致对局作废 | 房间 token + 状态快照恢复，超时判负给明确提示 |
| 时钟漂移误判超时 | 服务端时间为唯一裁决 |
| 课程标准自编不权威 | 只写有定论的基本型，标注来源 |
| 练习同质化、学生背题 | 生成器随机布子，每次进入局面不同 |
